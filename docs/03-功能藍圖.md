# 03 · 功能藍圖：接下來做什麼、什麼不要做

這份文件是「想法的排序」，不是待辦清單。**排序的標準只有一個：使用者站在櫃檯前的那 5 秒，這個功能有沒有幫上忙。**

現在的 App 已經能回答「刷哪張」。下面是我認為值得加、以及刻意建議不要加的東西。

---

## 已經在這一版做掉的

| 項目 | 說明 |
| --- | --- |
| 新 LOGO | 條碼化的 P + 台灣各支付品牌色漸層，見本文最後一節 |
| 多組手動條碼 | 手機條碼、自然人憑證、捐贈碼、會員條碼、自訂，可存多組並在全螢幕模式間切換 |
| 支付工具補齊 | 從 8 種擴到 22 種，含 9 家專營電支、TWQR、銀行錢包、通路錢包、三大手機感應 |
| 海外模式 | 日本／韓國通路與地標，回饋引擎會判斷地區，不讓台灣的 `all` 規則跨國生效 |
| 優惠變動偵測 | 每天檢查官方頁有沒有改，有改就開 issue 叫你核對（不自動改數字） |

| 金額換算 | 輸入金額直接顯示「約回饋 NT$X」，並把剩餘額度算進去 |
| 附近門市快選 | 定位成功但不在收錄門市時，列出 800 公尺內的門市讓你一鍵修正 |
| 通路分類細化 | 97 個通路分成 19 類，下拉選單可搜尋 |
| 條碼自訂名稱 | 可命名、可改名，會員卡有 14 個常見通路快選 |

---

## 第一優先：條件提示（登錄了嗎？門檻到了嗎？）

台灣信用卡的回饋幾乎都有前置條件：當月一般消費滿額、要先到銀行網頁登錄活動、指定通路才算。**沒登錄就是 0 加碼**，這是最常見的「以為有拿到」。

做法：規則資料加 `requires` 欄位（例如 `["每月需登錄", "當月一般消費滿 3000"]`），推薦卡片顯示成可勾選的檢查項，使用者勾過的記在本地，每月 1 號自動清空並提醒「這個月還沒登錄」。

這件事的價值不在功能複雜度，在於它把「使用者以為的回饋」和「實際會拿到的回饋」對齊——跟回饋上限追蹤是同一個問題的另一半。

---

## 第三優先：讓自訂卡片可以互相分享

自訂卡片與備份碼都已經做好了，下一步是把它變成社群資產：使用者把自己整理好的卡片規則透過備份碼分享出來，別人貼上就有。

再進一步是「回報規則」：使用者發現內建規則過期，一鍵產生一段可貼到 GitHub issue 的文字。這樣資料維護就不是只有你一個人在做——這是唯一能讓收錄卡片數突破個人維護上限的方法。

---

## 值得做但可以晚一點

- **金額輸入 → 實拿金額**：輸入 500 元，直接顯示「回饋 17 元」而不是 3.4%。百分比要換算，金額不用想。
- **繳費場景**：水電、稅、停車費的回饋規則跟一般消費完全不同（常常是 0%）。台灣 Pay 在這裡才是主角。
- **通路自動辨識加強**：門市資料從 40 筆擴到全台，才能真正做到「走進去就跳出來」。這是資料工程，不是功能開發，見 `docs/02`。
- **回饋幣別與點數換算**：街口幣、LINE POINTS、小樹點、momo 幣的實際價值不一樣（有的會過期、有的只能在特定通路折抵）。同樣 3% 不等值，這件事目前沒有任何 App 講清楚。
- **Widget / 鎖定畫面**：PWA 做不到，要原生 App。等真的有使用者再說。
- **每張卡的帳單結算日（觀察中，2026-08）**：查證發現回饋上限有些卡是日曆月計算、有些是帳單月計算，因銀行/活動而異，沒有統一規則。受益範圍不明確（多數常見活動查到的是日曆月為主），先不做，等真的有使用者反應「上限算錯」再回頭評估要不要加「每張卡選擇性覆寫成帳單月」的設定。

---

## 我建議不要做

| 想法 | 為什麼不建議 |
| --- | --- |
| 自動抓取並直接套用優惠 | 誤讀一個「需登錄」就會讓人少賺錢，比沒功能更糟。詳見 `docs/04` |
| 幫使用者查發票 / 對獎 | 已決定不做這個功能。需要財政部消費者 API（查詢個人載具明細）個人申請不到；統一發票中獎號碼雖然有較簡單的公開查詢方式，但評估後決定整個拿掉，不維護 |
| 帳號登入與雲端同步 | 一旦存了使用者的財務資料在你的伺服器上，你就進入個資法與資安的責任範圍。用分享碼解決換機問題就好 |
| 社群功能、回饋排行榜 | 這是工具，不是社群。使用者在櫃檯前不需要看別人刷了什麼 |
| 什麼卡都收錄 | 收 200 張卡但數字都過期，比收 20 張都準確要糟。維護成本是真實的 |
| 用 AI 即時解讀優惠條文 | 每次結帳都要等 LLM 回應，而且會產生看起來很有信心的錯誤數字。要用 AI，用在「維護資料時輔助人工」，不要放在使用者的關鍵路徑上 |

---

## 一個提醒

這個 App 的價值不是「功能多」，是「站在櫃檯前 3 秒能相信它」。每次要加東西，先問：**這會讓那 3 秒變快，還是變慢？**

回饋數字錯了會讓人少賺錢，這是會被罵的；App 少一個功能，沒人會發現。所以優先修正確性，再加功能。

## 附：LOGO 設計說明

`public/favicon.svg` 是所有圖示的來源檔，PNG 由它的幾何規格產生。

**構成：**

- **P 的直筆是三根粗細不同的直條**，像 Code 39 條碼的粗細條組合。這是整個 App 的核心動作——把條碼給店員掃。三根條分別用街口橘、悠遊藍、白，暗示「多家支付整合在一起」。
- **P 的碗是一道漸層描邊**，色彩依序掃過街口橘 → 全支付紅 → LINE Pay 綠 → 悠遊付藍 → 台灣 Pay 青。這是「結合台灣各大支付」的視覺主張，但用的是抽象色譜，沒有取用任何一家的商標或圖形。
- **深色圓角底 + 留白**，在 iOS 主畫面上跟一般 App 圖示的視覺語言一致。

**為什麼不做成 PayPay 那樣：** PayPay 的識別是「紅底 + 白色 PayPay 字樣」，那組合本身就是它的商標。要避免混淆，我刻意反過來走：深底、不用文字、不用單一紅色、主體是字母造型而不是品牌名。

**如果你要商業化，這幾件事要注意：**

1. 名稱「PayNav」與 LOGO 建議先到經濟部智慧財產局的商標檢索系統查一下有沒有近似案件，再考慮申請註冊。
2. 不要在 App 裡使用各支付品牌的官方 LOGO 圖檔。要顯示品牌，用文字名稱加自訂色塊（現在的做法就是這樣）。
3. 品牌色我用的是「近似色」而非各家的精確色票，這是刻意的。
4. 這些是一般性的注意事項，不是法律意見。真的要上架收費，找律師看一次比較保險。
