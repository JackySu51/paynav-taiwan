# 06 · 地標包：分區下載、刪除、更新

你要的是完整圖資，不是示範點位。這一版把架構做完了，**圖資由你在自己電腦上跑一行指令抓下來**——原因寫在最後一節。

## 使用者看到什麼

App 底部多了「地標」分頁：

- **已下載的地標**：門市數、地區數、實際佔用空間
- **自動更新開關**：目前鎖著，標示為付費解鎖
- **地區清單**：按 🇹🇼 🇯🇵 🇰🇷 分頁，每個地區顯示門市數與檔案大小，可個別下載／刪除／更新

一共 34 個地區包：

| 國家 | 地區 |
| --- | --- |
| 台灣 | 22 個縣市全覆蓋 |
| 日本 | 東京都、大阪府、京都市、福岡市、札幌市、名古屋市、沖繩本島 |
| 韓國 | 首爾、釜山、濟州、大邱、仁川 |

只裝台北市大約 400KB；台北 + 新北 + 東京大約 2MB。**沒下載也能用**，內建的基本門市與手動切換通路都照常運作。

## 你要做的事：產製圖資

```bash
npm run packs:list                        # 看清單與狀態
npm run packs:build -- tw-taipei          # 產製台北市
npm run packs:build -- tw-taipei tw-newtaipei jp-tokyo
npm run packs:build -- --region TW        # 整個台灣 22 縣市（會跑十幾分鐘）
npm run packs:build -- --all              # 全部 34 個（很久，別在趕時間時跑）
```

跑完之後：

1. `public/data/packs/tw-taipei.json` 出現
2. `public/data/packs/index.json` 裡那一筆的 `status` 從 `pending` 變 `ready`，門市數與檔案大小換成實際數字
3. 用 GitHub Desktop commit 並 push，Cloudflare 部署後使用者就能下載

**建議的第一步：** 先只跑 `tw-taipei`，確認流程通順、數量合理，再決定要不要一次抓完。

## 資料從哪來

OpenStreetMap，透過 Overpass API。腳本會抓 `shop=convenience`、`shop=supermarket`、`amenity=cafe` 等標籤，再用內建的品牌對照表篩出連鎖店。

對照表在 `scripts/build-packs.mjs` 的 `BRAND_RULES`，三個地區都有：

- 台灣：7-ELEVEN、全家、萊爾富、OK、全聯、家樂福、大潤發、Costco、星巴克、路易莎、cama、麥當勞、摩斯、KFC、屈臣氏、康是美、寶雅
- 日本：セブン、ローソン、ファミリーマート、ドン・キホーテ、マツモトキヨシ、ビックカメラ、イオン、一蘭、吉野家…
- 韓國：CU、GS25、emart24、올리브영、다이소、컴포즈커피、롯데마트、신세계…

**抓回來的數量比預期少很多？** 通常是品牌名稱在當地 OSM 用了不同寫法。在 `BRAND_RULES` 對應的地區加一組正規表達式就好，例如台灣要加「美廉社」：

```js
['simple_mart', /simple\s?mart|美廉社/i],
```

記得同時在 `public/data/stores.json` 的 `channels` 加上這個通路，否則規則驗證會擋下來（`npm run check:rules` 會告訴你）。

## 授權：這件事要看清楚

OpenStreetMap 資料採 **ODbL** 授權。可以自由使用、修改、商業使用，但有兩個義務：

1. **標示來源。** App 的地標分頁底部已經寫上「© OpenStreetMap 貢獻者」，不要拿掉。
2. **衍生資料庫要同樣授權。** 如果你公開發布「改作後的資料庫本身」，那份資料庫也要以 ODbL 釋出。把 OSM 資料當成 App 的內容使用、標好來源，是最常見也最安全的用法。

台灣的門市另一條路是**政府資料開放平臺**（data.gov.tw）或各通路官方 API，授權條件通常更寬鬆（多為政府資料開放授權條款）。缺點是覆蓋率與更新頻率要自己評估，而且不同通路的格式各自不同，要寫多份轉換。

**如果 App 要商業化收費，這段建議請律師看一次。** 我不是律師，上面是一般性說明。

## 對 Overpass 要有禮貌

Overpass 是志工營運的免費服務。腳本已經做了這些節制：

- 每個包之間等 8 秒
- 兩個節點輪替、失敗重試兩次
- 單次查詢 170 秒超時
- User-Agent 標明用途

**不要把它放進 GitHub Actions 每天跑。** 門市資料半年更新一次就夠了，天天抓只會害到所有人，也會被封 IP。這是為什麼「自動更新」設計成 App 端去抓你 CDN 上的檔案，而不是即時去抓 OSM。

## 自動更新做成付費功能的設計

現在 `autoUpdatePacks` 開關是鎖住的，`premiumUnlocked` 在 `src/store/useAppStore.ts` 裡恆為 `false`。

要開通時的實作順序：

1. **接金流**（訂閱制建議用 Stripe 或藍新／綠界的訂閱 API）
2. **驗證憑證**——這一步必須在伺服器端。前端只能存「已解鎖」的旗標，而 localStorage 是使用者可以自己改的。所以要用 Cloudflare Worker 驗證訂閱狀態，回傳一個有時效的簽章。
3. **把 `premiumUnlocked` 改成從 Worker 取得**，而不是本地狀態。

`worker/` 目錄已經有 API 代理的骨架可以擴充。

**一個實話：** 靠「自動更新地標」收訂閱費不容易，因為使用者可以手動按更新，價值差距不明顯。更可能願意付錢的是**回饋上限追蹤**與**條件提示**（見 `docs/03`）——那兩個直接關係到「這個月我還能拿多少回饋」，價值感清楚得多。地標自動更新比較適合當成付費方案的附加價值，而不是主打賣點。

## 技術細節

**為什麼門市存 IndexedDB 而不是 localStorage：** localStorage 通常只有 5MB，而且是同步 API，寫入時會卡住畫面。一個縣市數百 KB，多裝幾個就爆。IndexedDB 沒這個限制，也不會凍畫面。`src/utils/packStore.ts` 用原生 API 實作，沒有多裝套件。

**Service Worker 刻意不快取地標包。** 下載後已經自己存進 IndexedDB，讓 Workbox 再快取一份等於同一份資料佔兩倍空間，而且快取項目上限一滿還會把包默默淘汰掉。`vite.config.ts` 裡對 `/data/packs/` 設了 `NetworkOnly`（只有 `index.json` 例外，它很小而且離線時要用）。

**效能實測：** 16,000 筆門市（約等於台北＋新北＋東京）做一次最近門市比對約 1.6 毫秒。Haversine 是 O(n) 線性掃描，這個量級完全不需要空間索引。全台 22 縣市（約 3 萬筆）也還在幾毫秒等級。

**下載逾時 60 秒。** 規則庫用 6 秒就夠，但東京包接近 1MB，行動網路下 6 秒會被自己的逾時砍掉——這是實作時抓到的 bug。

**去重用網格分桶。** 同品牌 25 公尺內視為同一間店（OSM 常有 node 與 way 重複記錄同一間店）。原本兩兩比對在東京要六千萬次運算，改成分桶後 8,000 筆只要 106 毫秒。
