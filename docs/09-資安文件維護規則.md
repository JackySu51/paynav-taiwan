# 09 · 資安文件維護規則

這份文件只做一件事：**規定 `SECURITY.md`、`.env.example`、`README.md` 的「架構與安全性」小節，什麼時候要一起改。**

這三份不是寫一次交差的文件，是跟著功能增加持續修正的活文件。這份規則存在的意義，是讓「要不要同步更新資安文件」這件事不用每次都重新想一遍。

---

## 觸發規則

| 加的東西 | 要同步改的地方 |
| --- | --- |
| 新增後端服務（Turso、Supabase Auth、任何 API） | `SECURITY.md` 補一段這個服務怎麼被保護／驗證；`.env.example` 補對應的環境變數名稱（就算還沒真的接上） |
| 新增會存取使用者資料的功能（登入、同步、分享） | `README.md` 的「架構與安全性」小節更新資料流程說明 |
| 修掉一個資安問題 | `SECURITY.md` 的「已知限制」移除對應項目；「更新紀錄」加一行 |
| 發現新的風險但還沒修 | 誠實列進 `SECURITY.md` 的「已知限制」，不要略過不寫 |
| 任何金鑰、憑證性質的新設定 | 一定先進 `.env.example`（放假值），絕對不要直接寫進程式碼 |

## 這份規則怎麼被執行

**這不是靠「記得要做」，是靠每次討論新功能時，主動對照這張表檢查一遍。** 如果你（或之後接手的任何人，不管是不是我）在做以下這幾件事，就代表觸發了上面某一條，該去補資安文件了：

- 寫任何 `fetch()` 或 API 呼叫連到你自己以外的服務
- 加任何形式的登入、Session、Token
- 讓使用者資料離開他自己的裝置（不管是同步、備份到雲端、或分享給別人）
- 新增任何 `.env` 裡要填的變數

## 為什麼要堅持這件事

這三份文件加起來，是這個專案在說一句話：**「我們知道自己在存什麼資料、知道怎麼保護、也願意讓外部檢查。」** 這句話比任何單一的技術措施都重要——因為它證明了資安是這個專案的持續實踐，不是事後補的裝飾。放著不更新，這三份文件就會變成謊言（寫著已經修好的問題其實還在、寫著不存在的防護其實沒做），那反而比完全不寫還糟。
