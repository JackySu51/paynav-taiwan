# 07 · 商業性評估

你要的是誠實評估，不是鼓勵。以下是我看到的機會、真實的天花板，以及三條可行路線。

**先講結論：這個 App 有真實需求，但「靠它賺錢」最現實的路徑是辦卡導流，而不是訂閱。而導流的天花板取決於你能不能取得聯盟行銷資格——那是商業關係問題，不是技術問題。**

---

## 一、需求是真的

台灣的信用卡回饋生態異常複雜：22 種支付工具、每家銀行每季換活動、加碼要登錄、有上限、分不同通路。金管會統計到 2026 年初，全台電子支付帳戶總使用人數已超過 3,800 萬人——平均每人有一個以上的電支帳戶，也就是說「站在櫃檯前不知道該用哪個」是全民級的日常困擾。

現有的替代方案都不好用：

| 現況 | 問題 |
| --- | --- |
| 記在腦袋裡 | 記不住，而且每季會變 |
| Google 搜「XX 通路 回饋」 | 站在櫃檯前來不及，而且搜到的文章常常過期 |
| 卡優、Money101 等比較網站 | 內容豐富但是「查資料」導向，不是「現在該按哪個」 |
| 銀行自家 App | 只講自己的卡，而且要開很多個 |

**你的差異化是「情境化的即時決策」**：偵測我在哪、我有什麼卡、直接排序。這個定位是對的。

## 二、天花板在哪

### 使用頻率：中等，不算高

理想情況：每天結帳兩三次，每次開一下。但真實行為是——**使用者用幾週之後，會把常去店家的最佳組合記在腦袋裡，就不開了**。7-11 用哪張、全聯用哪張，記住之後 App 就失去日常價值。

這不是設計失敗，這是這類工具的天性。留存的關鍵是**「不確定的時刻」**：換季換活動、去沒去過的店、出國。所以日韓海外模式其實是很聰明的方向——出國時的不確定性最高。

### 資料維護是永續成本

15 張卡、105 條規則，一季核對一次大約要幾小時。**收 50 張卡就變成幾乎全職的工作。** 這是這門生意真正的護城河，也是真正的成本。變動偵測（`docs/04`）能減輕負擔但不能取代人工判斷。

### 準確性風險是法律風險

如果使用者照你的推薦刷卡，結果因為你的數字過期而少拿回饋，理論上有客訴甚至求償的可能。**免責聲明要顯眼、要保留、資料要標更新日期。** 這件事別省。

### 通路資料的授權天花板

用 OpenStreetMap 的資料要遵守 ODbL（見 `docs/06`）。商業使用可以，但義務要做到。要更乾淨的資料就得談授權或自建，成本立刻跳一級。

## 三、三條變現路線

### 路線 A：辦卡導流（我認為最現實）

App 裡已經有 `AffiliatePromoCard`：偵測到使用者沒有的神卡在該通路明顯更強（高出 3% 以上）時才顯示。

**為什麼這條最現實：** 台灣信用卡聯盟行銷的單件報酬相對高（核卡成功的佣金通常是幾百到一兩千元等級，實際數字依方案而異），而且推薦時機自然——使用者正在看「我少賺了多少」，這時候看到辦卡建議不突兀。

**關鍵瓶頸不是技術，是資格。** 你需要：

1. 加入聯盟行銷平台（台灣有幾家專做金融商品導流的），或直接與銀行的數位行銷部門談
2. 通常會要求：網站/App 已上線、有基本流量、公司登記（個人比較難談）
3. 揭露義務：有些平台要求明確標示為推廣連結

**現在就可以做的事：** 先把 App 上線、累積真實使用數據（就算只有幾百個使用者），那是談判材料。同時 `rules.json` 的 `apply_url` 先放銀行官網，等有聯盟連結再換掉——資料結構已經預留好了。

**要守住的線：** 不要為了佣金把某張卡排在前面。一旦推薦順序被佣金污染，App 就失去存在的理由，而且使用者遲早會發現。演算法純粹按回饋率排序，導流卡片獨立顯示——現在的設計就是這樣，別動它。

### 路線 B：訂閱制（難，但不是不可能）

**不建議賣的：** 地標自動更新（使用者手動按一下就好，價值差距不明顯）。

**可能賣得動的：**

- **回饋上限追蹤的進階版**：基礎版已經做在免費功能裡（記一筆、看剩餘額度、上限滿了自動換卡）。
  能收費的是進階：多月歷史、年度總回饋報表、快到上限時主動提醒、多張卡的額度分配建議
- **條件提示與登錄提醒**：每月 1 號提醒「這幾張卡還沒登錄活動」。沒登錄就是 0 加碼，這是最常見的隱形損失
- **多人共用皮夾**：家庭方案，一家人共用卡片池

台灣使用者對工具類 App 訂閱的接受度偏低，定價要抓在**每月 30-50 元**這個「一杯咖啡都不到」的區間。以台灣市場規模估算，要靠訂閱養活一個人，大概需要幾千個付費用戶——這需要相當可觀的下載量。

### 路線 C：B2B（最穩，但變成另一種生意）

把回饋比較引擎做成 API 或白牌，賣給銀行、比價網站、電商。

**優點：** 一個客戶的收入可能超過幾千個 C 端使用者，而且對方會提供資料。
**缺點：** 這變成軟體外包/授權生意，跟你現在做的 C 端產品是兩種公司。

## 四、我建議的順序

1. **先上線，免費，不放任何變現。** 目標是驗證「有沒有人會第二次打開它」。這個數字比什麼都重要
2. **同時累積資料維護的節奏。** 一季核對一次，確認你受得了這個負擔——受不了的話後面都不用談
3. **有了幾百個真實使用者，去談聯盟行銷。** 帶著數據談比空手談容易得多
4. **導流開始有收入，再考慮訂閱功能。** 先做回饋上限追蹤，那是最有付費價值的
5. **B2B 等對方來找你。** 如果 App 做得好，會有人找

## 五、成本結構（好消息）

| 項目 | 月成本 |
| --- | --- |
| Cloudflare Pages | 0 元（免費額度非常寬鬆） |
| Cloudflare R2 | 0 元起（初期用不到） |
| GitHub Actions | 0 元（private repo 每月 2,000 分鐘） |
| 網域 | 約 30-100 元 |
| **合計** | **幾乎是零** |

Local-first 架構的最大商業優勢在這裡：**沒有伺服器成本，使用者成長不會讓帳單成長。** 你唯一的成本是自己的時間。這意味著你可以慢慢養，不用急著變現——這是很奢侈的位置，多數新創沒有。

## 六、三個真實風險

**1. 銀行或支付業者自己做。** 他們有資料、有通路。但他們沒有動機做「跨銀行比較」——那會讓自家卡輸給別人。這是你的結構性優勢，會長期存在。

**2. 比價網站往 App 延伸。** 卡優、Money101 有內容與流量，如果他們做 App，你的優勢只剩「情境化即時決策」的產品體驗。速度是你的武器。

**3. 你自己維護不下去。** 這是最可能的死法。一個人維護 15 張卡的季度更新是可持續的；50 張不是。**寧可收錄少但都準確。**

---

## 一句話總結

技術風險幾乎為零（架構簡單、成本為零、已經能跑）。真正的風險是**資料維護的持續性**與**取得導流資格的商業關係**。這兩件事都不是寫程式能解決的，但都可以從「先上線、累積真實使用者」開始。
