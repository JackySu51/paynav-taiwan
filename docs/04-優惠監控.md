# 04 · 優惠活動：為什麼是「監控」而不是「爬蟲」

你問優惠活動的爬蟲機制有沒有在計畫內。**原本沒有，現在有了，但做成的形式跟你想的可能不一樣。**

這一版加的是「變動偵測」：機器每天盯著官方頁面，發現有改動就開一張 GitHub issue 叫你去核對，數字仍然由你決定。機器不會自己改回饋率。

下面說明為什麼這樣設計。

---

## 全自動爬蟲的三個問題

### 1. 準確度：這是金錢類資料，錯了會讓人少賺錢

台灣的信用卡回饋條文長這樣：

> 一般消費滿 3,000 元（不含分期、繳稅、電子錢包儲值），且當期登錄活動，指定行動支付享 2% 加碼（回饋以小樹點發放，每月上限 500 點，需於次期帳單前折抵）

要從這段文字正確抽出「回饋率、上限、門檻、排除項目、是否需登錄、有效期間」六件事，而且**六件都不能錯**。漏掉「需登錄」，使用者以為有 3% 結果拿 1%；漏掉「不含分期」，推薦就是錯的。

用 LLM 抽也一樣：它會給你一個看起來很有信心的答案，錯了你不會知道。在推薦引擎裡，一個安靜的錯誤比一個明顯的缺漏危險得多。

### 2. 法律：那是別人的著作

銀行的活動頁面是受著作權保護的內容。把整頁抓下來、存進你的資料庫、再用自己的 App 重新呈現，這件事的風險不是零，尤其當你的 App 商業化之後。

這支腳本的設計刻意避開這一點：**只保存內容的雜湊指紋（16 個字元）與抓取時間，不保存原文、不重新發佈。** 你最終寫進 `rules.json` 的是你自己讀完官方公告後整理的數字與敘述，那是你的著作。

另外 `scripts/watch-promos.mjs` 會先檢查對方的 `robots.txt`，明確禁止就跳過並記錄原因。這不是法律義務的全部，但是最基本的網路禮貌。

### 3. 維護：寫死選擇器的爬蟲每季都會壞

銀行網站改版頻繁，而且大量使用 JavaScript 動態渲染（純 HTTP 抓回來常常是空殼，要動用無頭瀏覽器才拿得到內容，成本立刻跳一級）。針對 15 家銀行各寫一支解析器，等於給自己 15 個每季都會壞的東西。

指紋比對只依賴「這頁有沒有變」，改版不會誤報成資料錯誤，只會讓你多核對一次。

---

## 所以實際的機制是這樣

```text
每天台北 09:00
  ↓
GitHub Actions 跑 scripts/watch-promos.mjs
  ↓
讀 public/data/promo-sources.json 的官方頁清單
  ↓
檢查 robots.txt → 抓 HTML → 取可見文字 → 正規化（把日期、序號換成佔位符）→ 算雜湊
  ↓
和上次的雜湊比對
  ├─ 沒變 → 什麼都不做
  └─ 有變 → 開一張 issue，列出「哪一頁變了、要看哪個數字、影響哪幾張卡」
                ↓
        你花 10 分鐘核對 → 改 rules.json → commit
```

**分工是：機器負責「不要漏掉」，人負責「判斷數字」。** 前者機器做得比人好（沒人會每天去看 8 個銀行頁面），後者人做得比機器好。

## 怎麼用

```bash
npm run promo:report   # 看目前監控清單與上次檢查時間（不連外）
npm run promo:watch    # 立刻檢查一次
```

**加一個要監控的頁面**：編輯 `public/data/promo-sources.json`

```json
{
  "id": "yourbank_card",
  "label": "某銀行某卡權益頁",
  "url": "https://...",
  "cards": ["yourbank_card"],
  "watch": "行動支付加碼與每月上限"
}
```

`watch` 欄位會直接出現在 issue 裡，寫清楚「這頁要看哪個數字」，三個月後的你會感謝現在的你。

**指紋存在哪**：`data/promo-state.json`（不是 `public/data/`，因為這是內部狀態，不需要給 App 讀）。

## 正規化在做什麼

很多頁面每次載入都會變一點點（時間戳、隨機 token、輪播廣告），如果直接比對原文，你會每天收到一張假警報，兩週後就開始無視它——這比沒有監控更糟。

所以腳本會先把日期格式、10 碼以上的數字序列換成佔位符，再算雜湊。這樣「頁面實質內容有改」才會觸發。

## 誤報還是太多的話

三個調整方向，難度由低到高：

1. **改監控更精準的頁面**：不要盯首頁（廣告輪播每天變），盯那張卡的權益說明頁。
2. **只比對關鍵段落**：在 source 加 `contains` 欄位，只對包含「回饋」「加碼」「上限」的段落算指紋。
3. **人工加 AI 輔助**：頁面有變時，把新舊文字丟給 LLM 問「回饋相關的數字有變嗎」，把答案寫進 issue 當參考。注意這是**輔助你判斷**，不是自動更新資料——差別很重要。

## 什麼情況才值得做真正的爬蟲

如果哪天你要收錄 200 張卡、每週更新，人工核對就撐不住了。那時候的正確做法不是自己爬，而是：

- 找有授權的資料供應商（比價網站或金融資料商）
- 或用官方提供的 API／RSS（有些銀行有活動 RSS）
- 或做成社群協作：讓使用者回報「這張卡的數字不對了」，你只負責審核

在那之前，8 到 20 張主力卡 + 每天一次變動偵測 + 每月 10 分鐘人工核對，是投入報酬比最好的組合。
